# Wokwi for capture-clip firmware (ESP32-S3, ESP-IDF v6.1): research

Date: 2026-09-29. Tags: **VERIFIED** (source + date 2026-09-29), **INFERRED** (reasoned from verified facts), **UNVERIFIED** (not checked).
Sources used: Wokwi docs repo `github.com/wokwi/wokwi-docs` @ 96fec01 (2026-09-16), which is the source of docs.wokwi.com;
`github.com/wokwi/wokwi-cli` @ ffde06b (the same commit as the installed 0.27.1); `github.com/wokwi/wokwi-boards`;
`github.com/wokwi/esp32-test-binaries`; the `wokwi/wokwi-features` issues; wokwi.com/pricing; one local simulation run (section 7).

## TL;DR

- **Microphone: the ESP32-S3 I2S peripheral is not simulated at all.** A custom mic chip therefore can't help. Use a firmware "test audio injection" mode.
- **Deep sleep on the S3 does not work in the sim.** In our run, `esp_deep_sleep_start()` led to a `TG1WDT_SYS_RST` reset about 1 s later every time, and neither the ext0 nor the timer wake cause ever showed up.
- **Everything else we need boots fine on ESP-IDF v6.1:** 16 MB flash, 8 MB octal PSRAM, custom OTA partition table, and a USB-Serial/JTAG console that `wokwi-cli` captures.
- **Budget:** the free plan has **50 CI minutes/month** of *simulated* time. That is enough for a few dozen short runs, not a few dozen long network runs per round.

## 3. Microphone

- **No I2S or PDM microphone part exists.** The parts docs have none; wokwi-elements has only `big-/small-sound-sensor` (KY-037-style analog/digital modules, not I2S); feature request #55 "Microphone" is still open. VERIFIED: docs `parts/` listing, `gh api wokwi/wokwi-elements/contents/src`, wokwi-features #55.
- **Custom Chips API** (C → WASM, beta): it offers GPIO with `pin_watch` (RISING/FALLING/BOTH), timers (`timer_start_ns`), and UART, I2C-device, SPI-device and framebuffer APIs. There is no I2S API and no file I/O (VERIFIED: `docs/chips-api/*.md`). A WAV could only be compiled into the WASM or passed in through attributes (INFERRED).
- **Feasibility: not feasible on the S3, whatever the chip does.** The chip would have to be clocked by the S3's BCLK/WS. The S3's I2S peripheral isn't simulated, so it would drive no clock, and `i2s_channel_read()` would get no data (INFERRED from the ❌ above).
- Even on a chip where I2S works, bit-banging 1.024 MHz BCLK means about 2 million WASM pin callbacks per simulated second. That is very likely to be slow in wall time (INFERRED; no benchmark was run).
- **Alternative: a compile-time test-audio injection mode.** A `CONFIG_CLIP_SIM_AUDIO` Kconfig option replaces the mic read (`i2s_channel_read`) with samples from a flash-embedded WAV (`EMBED_FILES` / `target_add_binary_data`, or a raw file in the 8 MB data partition).
  - This is deterministic and cheap, and it tests everything downstream of the mic: buffering, encode, file write, upload.
  - What it can't test: the I2S driver config itself (slot width, 24-bit-in-32 alignment, which channel), which has to be checked on the first real board.
  - **Recommended.**

## 4. Networking

- The simulated ESP32 joins the open AP **`Wokwi-GUEST`** (channel 6; passing the channel skips the ~4 s scan). It gets "full internet access": HTTP, HTTPS and websockets, over TCP/UDP with no ICMP. VERIFIED: `guides/esp32-wifi.md`.
- **The Public Gateway is the default and the only option on the free plan.**
  - "All the traffic is monitored for security purposes, so **do not use it** for private or sensitive data. … may enforce limits if we notice excessive usage." VERIFIED: same file.
  - TLS runs end to end on the simulated ESP32, so the gateway sees encrypted bytes plus hostnames (INFERRED). Keys should still be throwaway or low-scope.
- **wokwi-cli has no gateway option.** The CLI source (0.27.1) contains no gateway or `net.forward` code, and the sim start API takes only firmware, elf, flashSize, chips and pause (VERIFIED: `wokwi-cli/packages/client/src/APITypes.ts`).
  - So CI runs are cloud-side and go through the Public Gateway, and the Private Gateway (`wokwigw`) doesn't apply to CI (INFERRED).
  - The Private Gateway is for browser/VS Code sims on paid plans. It is a local binary on TCP 9011 that needs no root, and it adds `host.wokwi.internal` and port forwards (VERIFIED: `guides/esp32-wifi.md`, `vscode/project-config.md`).
- Whether HTTPS to `generativelanguage.googleapis.com` / `api.github.com` actually succeeds from a CI run: **UNVERIFIED** (not tested, to save minutes). Wokwi's own CI has a passing S3 `wifi_station` job, but that only proves association, not HTTPS.
- Upload size: no documented body-size limit. Throughput through the simulated Wi-Fi and Public Gateway is **UNVERIFIED**. A 1–5 MB body could cost a lot of simulated seconds, and TLS/crypto runs under the 8 MHz instruction cap unless `cpuFrequency` is raised (INFERRED).

## 5. Automation (wokwi-cli 0.27.1, confirmed with `--help`)

- **Run flags:** `--timeout <ms>` (default 30000, simulated time), `--timeout-exit-code` (default 42), `--expect-text`, `--fail-text`, `--scenario <yaml>`, `--serial-log-file <path>`, `--elf`, `--diagram-file`, `--interactive`, `-q`, `--vcd-file`, `-g/--gdb-server-port`.
- **Screenshot flags:** `--screenshot-part/-time/-file`. These only matter for display parts.
- **Subcommands:** `init`, `lint`, `chip` (custom-chip build), `mcp` (experimental MCP server).
- **Scenario steps** (VERIFIED: `packages/cli/src/scenario/*.ts`): `delay` (units required), `wait-serial`, `write-serial`, `set-control` (`part-id`, `name` or deprecated `control`, `value`), `expect-pin` (`part-id`, `name`/`pin`, `value`), `expect-chip-output`, `take-screenshot`, `touch*`.
  - Gotcha: the docs' `expect-pin` example uses `expected:`, but the code reads `value`.
  - Pushbutton control: `pressed` = 1/0. A hold ≥ 1 s is `pressed: 1`, then `delay: 1200ms`, then `pressed: 0`.
- **wokwi.toml for ESP-IDF** (VERIFIED: `vscode/project-config.md`, local run):
  ```toml
  [wokwi]
  version = 1
  firmware = 'build/flasher_args.json'   # bootloader + partition table + otadata + app, at their offsets
  elf = 'build/<project>.elf'
  ```
  - A merged binary (`esptool merge_bin`) or `idf.py uf2` also works, but flasher_args.json needs no extra step.
  - Also available: `idf-wokwi` (`pip install idf-wokwi`, then `idf.py wokwi --expect-text/--expect-regex`, for IDF ≥ 6.0). It is optional and was not tried. VERIFIED docs: `wokwi-ci/idf-wokwi-usage.md`.

## 6. ESP-IDF v6.1 gotchas

- Wokwi's own CI builds `release-v6.1` hello_world and Wi-Fi station for esp32s3 and passes, run of 2026-09-29. That run also passed psram, usb_serial_jtag, adc, gpio, nvs and wifi jobs on `latest` (VERIFIED: esp32-test-binaries `build.sh`, run 36562315487).
- The v6.1 bootloader, octal PSRAM, 16 MB flash and OTA table ran cleanly in our run (VERIFIED).
- The PSRAM memory test costs about 0.9 s of simulated time on every boot. Set `CONFIG_SPIRAM_MEMTEST=n` in sim builds (VERIFIED timing from log; the fix is INFERRED).
- **Deep sleep on the S3 → watchdog reset loop** (section 2). Sim builds need a "fake sleep" path, e.g. log "SLEEP" and wait for the button in a light loop, or `esp_restart()` (INFERRED).
- No I2S (section 3).
- The 8 MHz instruction cap makes Opus/AAC encoding and TLS take far more *simulated* time, and simulated time is what's billed. Try `"cpuFrequency": "240"` on the chip. It costs wall time, not quota (INFERRED from the docs' description of the cap).
- Old issue (2024): octal PSRAM failed until configured correctly. With `psramType: "octal"` it now works (VERIFIED: #809 + local run).

## 7. End-to-end check (one simulation run, 20 s simulated)

- **Setup:** ESP-IDF v6.1 `hello_world`, copied to `/tmp/claude-1000/wokwi-hello` and modified. The app prints flash/PSRAM/partitions, then deep-sleeps with ext0 on GPIO0 plus a 6 s timer.
- **Config:** `sdkconfig.defaults` sets 16 MB flash, custom `partitions.csv` (nvs, otadata, phy, ota_0 3 MB, ota_1 3 MB, storage 8 MB), octal PSRAM and the USB-Serial/JTAG console. The diagram is `board-esp32-s3-devkitc-1` {flashSize 16, psramSize 8, psramType octal, serialInterface USB_SERIAL_JTAG} + pushbutton GPIO0→GND. A scenario presses the button 1 s after "SLEEPING".
- **Command:** `wokwi-cli . --timeout 20000 --scenario wake.scenario.yaml --serial-log-file serial.log`.
- **Build:** clean, app 0x297d0 bytes.
- **CLI:** "Detected IDF project", connected to Simulation API 1.0.0-20260927, token accepted.
- **Serial output:** USB-JTAG console output streamed and went to the log (27 kB).
- **Boot:** bootloader showed the custom table; "Found 8MB PSRAM device", `flash=16MB psram=8388608`, all 6 partitions listed.
- **`wait-serial` step:** matched.
- **Deep sleep:** failed as described in section 2, with a `TG1WDT_SYS_RST` reboot loop and wake cause always 0.
- **Result:** exit code 42 (timeout), 30.6 s wall time. About 20 s of the 50 min monthly quota was used.

## What this means for the plan

1. **Audio: build the injection mode, not a custom chip.**
   - Add a Kconfig "sim audio source" that swaps the I2S read for a flash-embedded 16 kHz WAV (e.g. 3–5 s of speech), behind a tiny `mic_read()` abstraction.
   - A custom chip is impossible on the S3 today because the I2S peripheral isn't simulated.
   - Verify the real I2S config on the first assembled board.
2. **Sleep: abstract deep sleep behind a `power_sleep()` call.** Its sim build logs a marker and waits for the GPIO0 button in a normal loop. The press-vs-hold logic can then be tested with `set-control` + `delay`. Real ext0/ext1 wake can only be checked on hardware.
3. **Budget:** 50 simulated minutes/month is about 3000 s.
   - Keep most tests short (boot + button + LED + injected-audio encode, about 5–15 s each with `cpuFrequency` raised and the PSRAM memtest off). About 100–200 of those fit per month.
   - Network runs (Wi-Fi + TLS + multi-MB upload) could each cost a minute or more. Budget perhaps 5–10 per round.
   - If rounds need more, Hobby (€5.6/mo annual, 200 min) quadruples the quota. This costs money, so it needs the owner's OK.
   - Always pass a tight `--timeout` and `--expect-text`/scenario so runs end early.
4. **Networking in sim: the Public Gateway is the only path from CI.**
   - Use throwaway, low-scope keys (a test GitHub repo token and a restricted Gemini key), never the real ones. Keep network tests few.
   - Better still, split the upload path so most sim runs stop before sending, with the HTTP client unit-tested on the host.
   - First confirm with one run that HTTPS to both APIs works from the sim, and measure the simulated seconds per MB (UNVERIFIED so far).
5. **Tooling to use:** `wokwi.toml` with `firmware='build/flasher_args.json'`; a diagram with `board-esp32-s3-devkitc-1` + attrs above + `wokwi-pushbutton` on `0` + `wokwi-rgb-led` (anode) + a potentiometer on the battery ADC pin; scenario YAML for press/hold; `--serial-log-file` for the review pages.
