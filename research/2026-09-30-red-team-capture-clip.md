# Red team: what breaks the capture clip in the owner's hands (2026-09-30)

Reviewer did not design this board and did not read `DECISIONS.md`. Read-only pass over
`boards/capture-clip` (spec, board.toml, circuit, layout, case fit and renders, fab files) and the
firmware (`boards/capture-clip/firmware/main`, `firmware/components/clip`). Nothing was built, run
or measured. Another agent was editing the button sampler in `main.c` and `sim/run.py`; nothing
below depends on that half-edited code.

How to read this:

- **INFERRED** = reasoned from the files or from memory of a datasheet, not measured and not
  re-read today. Everything about real-board behaviour is INFERRED: no board exists.
- "Cost after delivery": *Wi-Fi* = firmware update over Wi-Fi; *USB* = flash or re-provision from
  the laptop with the case closed; *owner fix* = something a non-solderer can do (file a part,
  add a sticker, reprint a case); *rework* = soldering, which the owner cannot do; *new board* =
  second order and shipment.
- `board.toml` and `PROGRESS.md` were being edited while this was written, so they are cited by
  section, not by line.
- Paths are relative to the repo root. `bc/` = `boards/capture-clip/`, `fw/` =
  `boards/capture-clip/firmware/main/`, `clip/` = `firmware/components/clip/`.
- The fab quote is for 2 assembled boards (`bc/fab/cost.json:4-7`). That spare covers a single
  assembly defect. It does not cover a design fault: both boards have it.

## The short version

1. The 3.3 V regulator was picked for its 9 V input rating and 0.3 µA sleep current. How it
   behaves when Wi-Fi switches on (a 0 to ~350 mA step) was never looked at, and there is only
   about 32 µF behind it. If the rail dips under 2.84 V the chip resets, and the firmware then
   retries at once, forever. This is the one finding that can make the core function (send a note
   on battery) fail on every board with no firmware cure better than "turn the radio down".
2. The case works against the device: the microphone hole is in the underside (blocked when the
   clip lies on a table), the button stands proud with no guard (pocket presses start 15-minute
   recordings), and the cap-to-switch gap is 0.2 mm, the same size as the print tolerance.
3. USB recovery is sound. Main button + reset pinhole gives the chip's built-in flashing mode,
   which no firmware can break, as long as no security eFuse is ever burned. So firmware faults
   are fixable; what matters is that the device does not drain or loop itself in the meantime.
4. Firmware has no loop breakers: a brown-out loop, a crash loop or a held button each keep the
   chip awake until the cell is flat.

## C. Firmware: fix before shipping

All of these are fixable later over Wi-Fi or USB. They are listed because, until fixed, they
drain the cell, lose notes or leave the device looking dead.

## What was checked and found sound

- **USB recovery with the case closed.** Main button on IO0 plus reset behind a pinhole, native
  USB on the fixed pins, no eFuse burned: the ROM flashing mode is reachable whatever the firmware
  does (`bc/src/circuit.rs:278-301`, `fit.json` `opening.SW2`). It stays true only while no
  security eFuse is burned.
- **Bad update.** Two slots, trial boot, rollback on crash or failed check
  (`bc/firmware/sdkconfig.defaults:11`, `fw/update.c`). The old firmware always survives.
- **Power path.** USB present: cell isolated and charging; USB absent: cell feeds the board; a
  reversed cell is blocked by analysis (`bc/src/circuit.rs:181-205`).
- **Dead cell on USB.** The board runs from USB through D2 while the charger trickle-charges.
- **Fast charge never overlaps Wi-Fi** in the state machine, the worker and `net_up`
  (`clip/clip_sm.c:288-293`, `fw/main.c:286-294`, `fw/net_wifi.c:69`), and the pin is hi-Z at
  reset and asleep.
- **Power cut while recording.** Page-by-page sync, recovery at boot (`fw/recorder.c:46-54`).
- **Antenna keep-out** is in the footprint and empty in the render.
- **Provisioning console** lists key names and lengths only, never values
  (`firmware/components/provision/provision_cmd.c:28`).
